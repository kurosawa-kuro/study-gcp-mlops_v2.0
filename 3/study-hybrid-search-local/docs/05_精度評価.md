## 3. 主要 metrics の解釈

### 3.1 NDCG@10 = 0.9822

- 上位 10 件の累積 gain を理想ランキングと比較した正規化値
- `1.0` が完璧 (理想順序と一致)、`0` が逆順
- **0.9822** = 上位 10 件のラベル分布が理想にほぼ一致 (合成データの構造が単純なため高めに出る)
- random baseline 期待値は label_gain `[0,1,3,7]` 下で **約 0.5 前後**

### 3.2 MAP = 0.9967

- Mean Average Precision (binary relevance: `label > 0` を relevant と扱う)
- relevant items を上位に集約できているか
- **0.9967** = relevant items が高ランクに集中

### 3.3 Recall@20 = 1.0

- 上位 20 件以内に relevant items を全件含めているか
- **1.0** = 全 relevant が top-20 に入った (eval per-query candidates ≤ 20 の上限効果)

### 3.4 random ベースライン超えの根拠

`label_gain=[0,1,3,7]` で「label≥1 が 50% 程度」「上位 10 件にランダム配置」した場合、NDCG@10 期待値は約 0.5。
**0.9822** はこれを **大きく上回る** ため、ranker が「学習結果に基づいて relevant を上位に押し上げている」ことの直接的証拠。

## 6. 限界と注意点

### 6.1 合成データ前提の評価

- 本評価は `synthetic_ranking_frames` (LambdaRank 用に意図的に学習しやすく設計された分布) に対する in-distribution 評価
- **実トラフィックの NDCG@10 を推定する根拠にはならない**
- 実 `ranking_log` で再評価する手順:
  1. `/search` を多様なクエリで複数回叩く (例: `make verify-pipeline` を複数回)
  2. `feedback_events` にも click / favorite を貯める
  3. `make train` 再実行 (Phase 3 trainer は ranking_log を loader 経由で読む拡張余地あり、Phase 4 で BQ loader へ昇格)

### 6.2 評価セット重複のリスク

- 学習データと評価データが共に `synthetic_ranking_frames(seed=42)` 由来 (`split_by_request_id` で query 単位 80/20 分割)
- query 単位では分離されているため leakage は無いが、**生成分布が同一**
- 実データ移行時 (Phase 4) はこのリスクが消える

### 6.3 NDCG@10 の天井効果

- eval per-query candidates ≤ 20 のため Recall@20 は構造的に 1.0 に張り付く
- 候補プール拡大 (例: candidate_pool_size を 100 → 500) で意味が出る
- Phase 3 では `setting.yaml::candidate_pool_size: 100` がデフォルト

### 6.4 metrics の絶対値が高すぎることの解釈

- 本数値 (0.98+) を「実運用での上限性能」と誤読しない
- LightGBM LambdaRank は label_gain と groups さえ揃えれば合成データを過学習しやすい
- **Phase 3 の役割**: rerank 経路が動くこと (3 系統 all non-zero、score が固定 fallback でない) を **構造的に保証** する
- **絶対値ベンチマーク** は Phase 4 以降 (実 BigQuery `ranking_log` による評価) の責務

# 第 II 部 — 補論

## 7. 評価指標の比較と LLM 評価の難しさ (教材補論)

> Phase 3 の **検索ランキング評価** が Phase 1 の **California Housing 回帰評価** と
> 何が違うか、なぜ LLM 系評価はさらに難しいのか、なぜ正解データの作成が困難かを
> 教材視点で整理する。

### 7.1 全体像

| | Phase 1: California Housing | Phase 3: 不動産ハイブリッド検索 | LLM 系 (生成タスク) |
|---|---|---|---|
| **タスク種別** | 回帰 (regression) | ランキング (learning-to-rank) | 生成 (open-ended generation) |
| **出力空間** | 実数 1 個 (中央値家賃) | アイテムの順列 (top-K) | 自然文 (無限) |
| **評価単位** | 1 サンプル / 1 予測 | 1 query / N 候補のグループ | 1 prompt / 多様な生成 |
| **代表指標** | RMSE, R², MAE | NDCG@K, MAP, Recall@K, MRR | BLEU, ROUGE, BERTScore, LLM-as-a-judge, win-rate |
| **正解の作りやすさ** | 客観的 (測定可能な実数) | 半客観的 (relevance label が必要) | 主観的・多義的 (理想出力は一意でない) |
| **モデル例** | LightGBM 回帰 | LightGBM LambdaRank | GPT-4o / Claude / Gemini など |

---

### 7.2 Phase 1 (回帰) と Phase 3 (ランキング) の違い

#### 7.2.1 タスクの違い

**Phase 1 (California Housing 回帰)**
- 入力: 物件特徴量 (緯度・経度・部屋数・人口など 8 列)
- 出力: **連続値 1 個** (中央値家賃 `MedHouseVal`)
- 学習データ: `(特徴量, 真の家賃)` の i.i.d. ペア
- 1 サンプル独立評価可能 (point-wise)

**Phase 3 (不動産ハイブリッド検索ランキング)**
- 入力: クエリ + フィルタ + 候補プール (BM25 + ANN で top-K=100)
- 出力: **候補の順序付け** (上位 N 件)
- 学習データ: `(query, 候補N件, ラベル N 個)` のグループ
- **per-query 評価必須** (list-wise / pair-wise) — 候補単独で評価できない

#### 7.2.2 学習データの作り方の違い

| | Phase 1 | Phase 3 |
|---|---|---|
| サンプル単位 | 1 物件 = 1 行 | 1 query = 1 グループ (候補 N 件) |
| 真値の出所 | 過去の取引データ (実測値) | **行動ログ** (click / favorite / inquiry) → ラベル変換 |
| 特徴量数 | 固定 (8 列) | 動的 (10 列 + query-time 信号: me5_score / lexical_rank / semantic_rank) |
| データ量の制約 | 行数だけ揃えればよい | **per-query 候補数のばらつき** が学習を不安定にする |

#### 7.2.3 モデル (LightGBM の objective が変わる)

| | Phase 1 | Phase 3 |
|---|---|---|
| objective | `regression` | `lambdarank` |
| 損失関数 | MSE (mean squared error) | LambdaRank loss (NDCG の微分近似) |
| group 引数 | 不要 | **必須** (per-query candidates の境界) |
| label | 連続値 (家賃) | 0..3 の段階 (`label_gain=[0,1,3,7]`) |

Phase 3 で `lgb.Dataset(..., group=train_groups)` を渡すのは、**「同じ query 内での順序」だけが意味を持つ** ことを LightGBM に明示するため。Phase 1 の LightGBM 回帰では group は不要。

#### 7.2.4 サンプル独立性の喪失

**Phase 1 では 1 サンプル交換が局所影響:**
```text
1 物件の予測誤差 → そのサンプルの (RMSE, R²) に寄与するだけ
```

**Phase 3 では 1 候補の順位ずれがグループ全体に伝播:**
```text
1 候補が上位 1 → 5 位に降格 → そのグループの NDCG@10 が大きく変動
                                → 上位 4 候補も「降格された候補が消えた分」の押し上げ効果
```

→ Phase 1 のテストは「ペア毎」で書ける、Phase 3 のテストは「query group ごと」に書く必要がある (例: `tests/_fakes/in_memory_candidate_retriever.py` は per-query 候補を返す API)。

---

### 7.3 評価指標の違い

#### 7.3.1 回帰指標 (Phase 1 系)

| 指標 | 定義 | 直感 |
|---|---|---|
| **RMSE** | √(Σ (y_pred − y_true)²/N) | 予測値と真値の **絶対誤差** (元の単位) |
| **MAE** | Σ \|y_pred − y_true\|/N | RMSE より外れ値に頑健な誤差 |
| **R²** | 1 − Σ(y_pred − y_true)² / Σ(y_true − ȳ)² | 平均予測ベースラインに対する説明率 |

**特徴**:
- 正解と予測値の **絶対距離** を測る
- 単一サンプルで意味が出る (point-wise)
- `0` がベスト (RMSE / MAE) または `1` がベスト (R²)

#### 7.3.2 ランキング指標 (Phase 3 系)

| 指標 | 定義 | 直感 |
|---|---|---|
| **NDCG@K** | Σ (2^label − 1)/log₂(rank+1) を理想順序で正規化 | 上位 K 件にどれだけ relevant が集中したか (位置に対して log で減衰) |
| **MAP** | per-query Precision@k の平均 | relevant items が高ランクに偏ったか (binary relevance) |
| **Recall@K** | 上位 K 件が含む relevant 数 / 全 relevant 数 | 上位 K に取りこぼしがないか |
| **MRR** | 1 / 最初の relevant item の rank | 「最初の正解までの距離」 |

**特徴**:
- **順序** だけが意味を持つ (絶対値は無関係)
- per-query 集計が必須 (`evaluate()` 関数は groups 引数を取る、本リポでは [`ml/evaluation/metrics/ranking.py`](../ml/evaluation/metrics/ranking.py))
- `[0, 1]` の正規化値、`1.0` が理想

#### 7.3.3 同じ「精度」でも測っているものが違う

| 観点 | 回帰指標 (RMSE) | ランキング指標 (NDCG) |
|---|---|---|
| 「何をどれだけ間違えたか」 | 数値の差 | 順位の入れ替わり |
| 1 個 ±10% ズレた時の影響 | 局所的 (そのサンプルの誤差にのみ寄与) | **大きい** (上位なら NDCG@K が劇変、下位なら無関係) |
| 単位 | 元データの単位 (USD 等) | 無次元 |
| ベースライン | mean predictor の R²=0 | random ranking の NDCG ≈ 0.5 (label gain 分布依存) |
| 業務指標との直結 | 直結しやすい (誤差金額 = 損失額) | 間接的 (NDCG↑ → CTR↑ を経由して売上) |

#### 7.3.4 指標選択のミスがプロジェクトを壊す例

- **検索を回帰指標で評価した**: 「全候補の `relevance_score` を回帰予測しても、それが正しい順序を生むとは限らない」 → 上位だけ間違ってる場合に RMSE は下がるが NDCG は下がる
- **回帰を NDCG で評価した**: 「家賃予測を順位で見ると、絶対値ズレが消えて見える」 → 業務 KPI (誤差金額) と乖離

→ **タスク種別と指標を必ず一致させる**。Phase 1 が RMSE / R²、Phase 3 が NDCG / MAP / Recall になっているのはこの原則の具体例。

---

### 7.4 なぜ LLM 系の精度評価は難しいのか

LLM 系 (生成タスク: 要約、QA、対話、コード生成、RAG など) は Phase 1 / Phase 3 とは **質的に異なる難しさ** を抱える。

#### 7.4.1 出力空間が事実上無限

- 回帰: ℝ (実数)、1 次元
- ランキング: 候補 N の順列 (有限)
- **LLM**: トークン列 (vocab^length)、**実質無限** に近い
- → 同じプロンプトに対する正解が **一意でない**

#### 7.4.2 同じ意味の表層差 (paraphrase)

```text
正解候補: "犬は哺乳類である。"
生成 A:  "犬は哺乳類だ。"               (語尾)
生成 B:  "イヌは哺乳類に分類される。"   (語彙)
生成 C:  "Dogs are mammals."           (言語)
```

すべて意味的に同等だが、**文字列マッチでは異なる**。
- BLEU / ROUGE: n-gram 一致率 → A は近い、B は遠い、C はゼロ
- BERTScore: embedding 距離 → A/B/C すべて高い類似度
- LLM-as-a-judge: 「同じ意味か?」を別 LLM に判定させる → 安定するが judge 自体が不完全

#### 7.4.3 正解が文脈依存

- 「明日の天気は?」 — 場所・時間・問い手の関心で正解が変わる
- 同じ質問でも、ユーザの背景次第で「良い回答」が違う
- → **静的な正解集合では評価できない**

#### 7.4.4 多次元の品質軸

LLM 出力は単一スカラーでは評価できない:

| 軸 | 例 |
|---|---|
| **Helpfulness** | ユーザの問いに答えているか |
| **Harmlessness** | 有害情報を生成していないか |
| **Honesty / Faithfulness** | 事実と乖離していないか (hallucination) |
| **Coherence** | 論理的一貫性 |
| **Fluency** | 自然な文章 |
| **Style** | tone / format / length が適切か |

→ 単一 NDCG / RMSE のような **1 数字** では捕まえきれない。Anthropic の HHH (Helpful / Harmless / Honest)、OpenAI の MMLU / TruthfulQA、Stanford HELM などはこの **多軸評価** の代表。

#### 7.4.5 Hallucination の検知

- 「事実に見える嘘」を生成する
- 文法・流暢さでは正しい、内容だけ間違っている
- 評価には **ground truth knowledge** が必要 → そもそも knowledge 自体を別 LLM や DB で検証する必要 (= 評価インフラが学習インフラ並みに重い)

#### 7.4.6 評価の自動化と人手評価のジレンマ

| 評価方式 | 長所 | 短所 |
|---|---|---|
| **自動メトリクス** (BLEU / ROUGE / BERTScore) | 高速・再現可能 | 表層に偏る、人間の好みと相関弱い |
| **LLM-as-a-judge** (GPT-4o などで採点) | スケール可、多軸評価可 | judge LLM の bias が伝播、cost、prompt sensitivity |
| **人手評価 (annotator)** | gold standard | 高コスト、annotator 間で不一致 (κ 値低い)、annotation drift |
| **A/B テスト (実 traffic)** | 業務 KPI と直結 | 時間がかかる、有害な悪化を本番で晒すリスク |

LLM 系では **複数を組み合わせる** のが標準 (例: 自動 → LLM judge → 人手 sample) が、それでも完全な評価は難しい。

#### 7.4.7 評価が常に学習に流入するリスク

- 同じテストセットで何度も評価 → モデル開発者がそのテストに最適化 (test set leakage の人間版)
- public benchmark は数年で「飽和」(MMLU は 2024 年で頭打ち)
- → 評価データを **継続的に作り直す** 必要 (cost が更に増える)

---

### 7.5 なぜ LLM 系の正解データを作るのが難しいのか

評価指標が決まっても、**「正解」の作成自体が難しい**。これが LLM 評価の最大のボトルネック。

#### 7.5.1 高品質ラベルの希少性

| タスク | 正解作成のコスト要因 |
|---|---|
| 翻訳 | プロ翻訳者のレート (~$0.10/word) |
| 法律 QA | 弁護士 / 法務の知識 |
| 医療 QA | 医師 / 専門医、誤情報の責任問題 |
| コード生成 | 動作テスト + コードレビュー |
| 要約 | 元文書を熟読 → 要約 → 別人がレビュー |

→ 1 サンプル作るのに **数分〜数十分**。10,000 サンプル作るのに人月単位。

#### 7.5.2 Inter-annotator agreement (IAA) の低さ

- 同じ prompt に対して、annotator A と annotator B の正解が違う
- Cohen の κ (annotator 一致度) は LLM 系で **0.3-0.6** が一般的 (回帰の数値ラベルなら ~0.95)
- 一致度が低いラベルで学習すると **モデルは何を最適化しているか不明** になる

#### 7.5.3 主観性

- 「良い回答」は読み手依存 (専門家 vs 初心者)
- 文化・言語・年代でも変わる
- 「正解 1 つ」を仮定するパラダイムが崩れる
- → **複数正解** / **rank された正解** / **rejection sampling** の枠組みが必要 (DPO / RLHF 系の前提)

#### 7.5.4 自動生成のリスク (synthetic data trap)

- 「LLM に正解データを作らせる」アプローチ
- メリット: 大量・高速・低コスト
- デメリット:
  - **生成器の bias** がそのままデータに乗る
  - **distribution の偏り** (例: GPT-4o で作った QA は GPT-4o-like な答えに最適化される)
  - **ground truth fidelity** が落ちる (ハルシネーションが正解として混入)
- → 結局、人手 annotation が必要

#### 7.5.5 動的な正解の変化

- 時事問題 (「2024 年のオリンピック開催地」) は時間で正解が変わる
- 法律・医学知識も update される
- → **正解データセットの賞味期限** が短い

#### 7.5.6 ランキングタスクでも同じ問題が現れる

実は Phase 3 の検索ランキングでも、本番運用では LLM 系と類似の問題が起きる:

| 問題 | Phase 3 検索での例 |
|---|---|
| **Position bias** | ユーザは上位を click しやすい → 既存ランカーの偏った評価が再帰する |
| **Selection bias** | 上位 10 件しか見えない → 11 位以降の真の relevance が分からない |
| **Click ≠ relevance** | クリックは relevance のノイジな proxy (ミスクリック / 後悔クリック) |
| **Dwell time bias** | 滞在時間が長い = 良い? → 単に複雑で読み解けないだけかも |
| **Counterfactual evaluation の必要性** | 「もし別ランカーで提示してたら何がクリックされたか」は観測できない |

→ Phase 3 では `synthetic_ranking_frames` で逃げているが、本番では **実 click ログから offline policy evaluation** (IPS / DR / DM 推定) が必要になる。これは LLM 系の「正解作りの難しさ」と地続きの問題。

---

### 7.6 Phase 3 で学べることと学べないこと

#### 7.6.1 Phase 3 で学べる (本リポ範囲)

- Phase 1 の **回帰指標 (RMSE / R²)** との対比でランキング指標 (**NDCG / MAP / Recall**) が必要な理由
- LightGBM の `lambdarank` objective と `group` 引数の意味
- per-query 評価を `evaluate(labels, scores, groups, k_ndcg, k_recall)` (本リポ [`ml/evaluation/metrics/ranking.py`](../ml/evaluation/metrics/ranking.py)) で行う具体的コード
- 3 系統 (lexical / semantic / rerank) all non-zero で動かす structural な保証
- Phase 4 で BQ ranking_log loader に差し替えても評価コードを変えずに動く構造 (Port 同型)

#### 7.6.2 Phase 3 では学べない (Phase 4-7 / 別教材の責務)

- 実 traffic での counterfactual evaluation (IPS / DR)
- LLM 系の generation 評価 (BLEU / ROUGE / BERTScore / LLM-as-a-judge)
- annotator pipeline の構築 (RLHF / DPO 用の preference data)
- A/B テスト基盤 (Phase 6 の SLO + burn-rate alert は近いが、ranking quality の A/B は別)

#### 7.6.3 「なぜ評価が難しい?」の一般原則

1. **タスクが複雑になるほど指標が多軸化** (回帰 1 軸 → ランキング 4-5 軸 → 生成 数十軸)
2. **正解の作成コストが指数的に上がる** (測定値 → relevance label → preference / 全文)
3. **評価データ自体が劣化する** (時間経過 / leakage / bias)
4. **業務 KPI との直結度が下がる** (技術的な NDCG ↑ → CTR ↑ → 売上 ↑ の連鎖が長くなる)

→ **評価は学習と同じくらい (場合によりそれ以上に) 難しい**。Phase 3 はその第一歩 (回帰 → ランキング への移行)、Phase 7 完成版でも本格的な評価インフラは PMLE 4 技術 (TreeSHAP Explainability / Monitoring SLO + burn-rate / drift detection) で補強される設計。
