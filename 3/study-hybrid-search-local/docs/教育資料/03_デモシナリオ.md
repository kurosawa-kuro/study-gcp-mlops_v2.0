# ハイブリッド検索デモシナリオ

**目的:** スライドで説明した `lexical 候補 + semantic 候補 → RRF → LightGBM rerank → ログ` の流れを、API とコードで短く見せる。Phase 1 (住宅価格予測) との違いも対比する  
**想定尺:** 7〜9 分  
**画面:** ターミナル + エディタ + API レスポンス + Web UI (`http://localhost:8000/ui/`)

---

## デモ全体の流れ

0. **Phase 1 との違いを 30 秒で確認** (回帰 vs ランキング)
1. `SearchRequest` を確認して入力項目を把握する
2. `SearchService.run` を開いて主処理を読む
3. `curl /search` を実行してレスポンスを見る
4. `LocalLightGBMReranker` を見て、ME5 スコアが特徴量の 1 つに過ぎないことを確認
5. `top_k` / フィルタを変えて挙動の違いを話す
6. 評価指標と正解データの話で締める

---

## Step 0: Phase 1 との違いを 30 秒で確認

### 伝えること

| 観点 | Phase 1 (住宅価格予測) | Phase 3 (ハイブリッド検索) |
|---|---|---|
| 出力 | 価格 (数値) | 順位付き Top-K |
| 目的関数 | 二乗誤差最小化 | LambdaRank (NDCG 直接最大化) |
| 評価指標 | RMSE / MAE | NDCG / MAP / Recall@K |
| 正解データ | 成約価格 (明確) | 行動ログ (バイアス混入) |

### ナレーション要点

> Phase 1 の住宅価格予測は「数値を当てる」回帰タスクでした。  
> Phase 3 は「どの順番で出すか」を決めるランキングタスクです。  
> 同じ LightGBM を使っていても、目的関数も評価指標も別物です。  
> 本デモでは「順序」「複数指標」「行動ログ」が主役、と最初に押さえてください。

## Step 2: 主処理の確認

### 開くファイル

- `app/services/search_service.py` (`SearchService.run`)
- `app/services/ranking.py` (`run_search` + `rrf_fuse`)
- `app/services/adapters/local_candidate_retriever.py` (lexical + semantic 統合)

### 注目行 (`SearchService.run` の流れ)

- `lexical_search_port.search` (Meilisearch BM25 + filter)
- `encoder_client.encode` (multilingual-e5 で query 埋め込み)
- `semantic_search_port.search` (pgvector cosine 近傍)
- `rrf_fuse` (Reciprocal Rank Fusion)
- `feature_fetcher.fetch_features` (`feature_mart_property_features_daily`)
- `reranker_client.rerank` (LightGBM Booster)
- `ranking_log_publisher.publish` (`ranking_log` INSERT)

### ナレーション要点

> 検索の主線はここです。  
> このコードはキーワード検索とベクトル検索を **両方走らせて RRF で融合** する形です。  
> ベクトル側は multilingual-e5 でクエリをベクトル化し、pgvector の cosine 距離 (`<=>`) で近傍を取ります。  
> 物件側のベクトルは事前に `embeddings` テーブルに格納してあり、`make seed` で投入されています。  
> 融合した候補に行動系特徴を足し、LightGBM で並べ替え、最後にログを残します。  
> この順番を頭に入れておくと、後続のアダプタ実装が読みやすくなります。

## Step 3: API を叩く

### 例コマンド

```bash
curl -s -X POST http://localhost:8000/search \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "駅近 静かな住宅街 2LDK",
    "filters": {"max_rent": 150000, "layout": "2LDK", "pet_ok": true},
    "top_k": 5
  }' | jq
```

### 画面で見るポイント

- `items[]`
- 各 item の `lexical_rank` / `semantic_rank` / `final_rank`
- 各 item の `score` (LightGBM rerank 出力)
- `request_id` (後段の `/feedback` と紐付く)

### ナレーション要点

> 各 item の 3 つの rank が **all non-zero** であることに注目してください。  
> これは lexical / semantic / rerank の 3 系統が全部動いている証拠です。  
> `score` が固定 fallback (0.0) でないことも、学習済モデルが効いている証拠です。  
> Web UI (`http://localhost:8000/ui/`) でも同じレスポンスをカード表示で確認できます。

## Step 4: 再ランキングの中身を見る

### 開くファイル

- `app/services/adapters/local_lightgbm_reranker.py` (`LocalLightGBMReranker`)
- `ml/data/feature_engineering/schema.py` (`FEATURE_COLS_RANKER` 10 列)

### 見せる箇所

- `Booster.load_model(model_path)` で `model.lgb` を起動時に読み込む
- 特徴量行列の組み立て: 検索系 3 列 + 物件属性 4 列 + 行動系 3 列
- `Booster.predict(matrix)` で score 取得
- score 降順で `final_rank` を再付与

### ナレーション要点

> 注目すべきは「ME5 のスコアは順位そのものではなく、特徴量の 1 つ」という点です。  
> LightGBM は ME5 スコア + lexical 順位 + semantic 順位 + 物件属性 (rent / walk_min / age / area) + 行動ログ (ctr / fav_rate / inquiry_rate) を束ねて並べ替えます。  
> 単一スコアでは取れない「総合判定」が機械学習の出番です。  
> 行動系特徴は `feature_mart_property_features_daily` から取ってきていて、`make seed` で日次集計済の状態を作っています。

## Step 4.5: 学習側 LightGBM の目的関数を確認

### 開くファイル

- `ml/training/trainer.py`

### 見せる箇所

```python
params = {
    "objective": "lambdarank",
    "metric": "ndcg",
    "ndcg_eval_at": [10],
    ...
}
train_set = lgb.Dataset(x, label=y, group=group_sizes, ...)
```

### 強調したい 3 点

- `objective = lambdarank` — ペアワイズランキング損失、NDCG を直接最大化する目的関数
- `group = group_sizes` — 同じ検索クエリの候補群をまとめて LightGBM に教える (順序比較はクエリ内に閉じる)
- `metric = ndcg` / `ndcg_eval_at = [10]` — 上位 10 件の NDCG を学習中に監視

### ナレーション要点

> 再ランキングで使っているモデルは、Phase 1 の住宅価格予測とは別種の学習をしています。  
> Phase 1 は二乗誤差を最小化する回帰でした。今回の LambdaRank は、同じ検索クエリ内の順序関係をペアワイズで学びに行きます。  
> `group_sizes` でクエリ単位のグルーピングを LightGBM に伝えているのが鍵です。

## Step 4.6: 精度評価が難しい理由

### 開くファイル

- `docs/05_精度評価.md` §3 (Phase 3 実測の解釈)
- `ml/evaluation/metrics/ranking.py` (`evaluate` / NDCG / MAP / Recall 実装)

### 見せる箇所

- `evaluate(labels, scores, groups, k_ndcg=10, k_recall=20)` のシグネチャ
- query 単位 (group) で集計してから平均する関数構造
- `LABEL_GAIN = [0, 1, 3, 7]` (none / click / favorite / inquiry)

### ナレーション要点

> Phase 1 の住宅価格予測は誤差 (RMSE) で評価できました。1 つの数値で済みます。  
> Phase 3 の検索は「正解が一意でない」ため Recall@K / NDCG / MAP を **複数指標で** 見ます。  
> 本実装でも NDCG@10 で高い値を達成していますが、これは **合成ログでの in-distribution 評価** であり、本番ログでの再評価が次のステップです (詳細は 05_精度評価.md)。  
> 行動ログには表示位置バイアスがあり、「クリックされた = 良い結果」とは必ずしも言えません。

## Step 5: `top_k` とフィルタの話

### 追加コマンド例

```bash
curl -s -X POST http://localhost:8000/search \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "駅近 静かな住宅街 2LDK",
    "filters": {"max_rent": 200000},
    "top_k": 20
  }' | jq '.items[] | {final_rank, lexical_rank, semantic_rank, score}'
```

### 比較観点

- 上位の並びが入れ替わるか
- フィルタを緩めると候補が広がり、rerank の効きが見える
- レスポンス時間 (Redis cache の効果)

### ナレーション要点

> `top_k` を増やすと、より良い候補が後段に渡る可能性があります。  
> その代わり、特徴量取得や rerank のコストは増えます。  
> フィルタの強さと `top_k` の幅は、精度と速度のバランスを見る代表的なチューニングポイントです。

## Step 5.5: なぜ正解データ作成が難しいか

### 開くファイル

- `app/api/routers/feedback_router.py` (`POST /feedback`)
- `definitions/postgres/migrations/0001_init.sql` の `feedback_events` / `ranking_log`

### Web UI 操作 (任意)

- `http://localhost:8000/ui/` で検索 → カードの `click` / `favorite` / `inquiry` ボタンを押す
- `docker exec phase3-postgres psql -U admin -d hybrid_search -c 'SELECT * FROM feedback_events;'` で確認

### ナレーション要点

> `/feedback` の click / favorite / inquiry が、再学習の「正解候補」になります。  
> `LABEL_GAIN = [0, 1, 3, 7]` で行動の重みを変えていますが、これらは **「真の良さ」ではなく「行動の痕跡」** です。  
> 表示位置バイアス、写真の見栄え、価格の安さなど、行動以外の要因が混入します。  
> そのため実案件では、**人手評価 / LLM-as-a-Judge / オンライン A/B** など複数チャネルで補正します。  
> 「モデルを良くする」より「正解データを良くする」ほうが効くことも多い、というのが検索 MLOps の感覚です。

## Step 6: 締め

### 伝えること

- ハイブリッド検索は段階分担で考える (lexical / semantic / rerank)
- 評価指標は **複数** (NDCG / MAP / Recall + CTR / CVR / 問い合わせ率)
- 正解データの作り方が改善の出発点
- Phase 4 以降は実行基盤が変わるが、思想 (Port/Adapter) と評価軸は引き継がれる

### クロージング例

> このプロジェクトでは、検索エンジン、埋め込み、学習済モデル、ログ保存を **Port/Adapter で分けて** 実装しています。  
> そのため、どこを改善すれば品質が上がるかを切り分けやすい構造です。  
> Phase 4 以降は同じ Port を保ったまま、adapter を BigQuery / Vertex AI / GKE に差し替えていきます。  
> 不変は **「不動産ハイブリッド検索」というテーマと評価の考え方** です。
