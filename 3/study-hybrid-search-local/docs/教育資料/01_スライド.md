# ハイブリッド検索入門

不動産検索を題材に  
**lexical + semantic + rerank** を学ぶ

---

## この Phase の主眼

- 検索を 1 つのモデルではなく、複数段の処理で考える
- `Meilisearch` / `multilingual-e5` / `LightGBM LambdaRank` の役割分担を理解する
- `Redis` を使ったキャッシュの位置づけをつかむ

---

## なぜハイブリッド検索か

| 手法 | 強み | 弱み |
|---|---|---|
| lexical search | 速い、厳密条件に強い | 言い換えに弱い |
| semantic search | 意味の近さに強い | 構造化条件が苦手 |
| rerank | 複数特徴をまとめて最終調整できる | 単独では候補を集めにくい |

---

## Phase 1 との対比 — 回帰 vs ランキング

- Phase 1: 住宅価格を **数値で予測** (RMSE / MAE で誤差を測れる)
- Phase 3: 検索結果を **順序で提示** (NDCG / MAP / Recall@K で品質を測る)
- 目的関数も違う — 二乗誤差最小化 ↔ LambdaRank (NDCG 直接最大化)
- 「正解の作りやすさ」も大きく異なる (後ろのスライドで詳述)

> ML の難しさの種類が違うことを最初に押さえる。

---

## 従来検索とハイブリッド検索の違い

| 観点 | 従来 (lexical のみ) | ハイブリッド検索 |
|---|---|---|
| マッチ方法 | キーワード一致 / BM25 | 一致 + 意味近傍 + 並べ替え |
| 言い換え | 弱い | 拾える |
| 構造化条件 | 強い | 強い (lexical 側で担当) |
| 改善余地 | 同義語辞書 | 特徴量・ログ・モデル |

→ 単一手法では拾えない検索意図を、3 段で補い合う。

---

## 3 段構成

```text
1. Meilisearch で候補取得
2. multilingual-e5 で意味類似度を計算
3. LightGBM LambdaRank で最終順位を決める
```

> この Phase の中核は `LightGBM + multilingual-e5 + Meilisearch`。

---

## Meilisearch を使う理由

- `Elasticsearch` より導入しやすい
- 学習用ローカル構成でも扱いやすい
- 厳密条件の絞り込みを高速に試せる
- BM25 ベースの lexical search を素直に体験しやすい

---

## semantic search の役割

- クエリと物件説明文を embedding に変換する
- 完全一致しない表現も「意味の近さ」で拾う

例:

- `静かな住宅街`
- `閑静なエリア`

> 表記一致ではなく意味近傍で候補を補う。

---

## ベクトル検索とベクトル DB

- 文書とクエリを Embedding でベクトル化 → 近さで検索
- 完全一致しなくても意味が近ければ拾える
- 格納先は Phase ごとに置換可能:
  - **PostgreSQL + pgvector** (Phase 3 採用)
  - BigQuery `VECTOR_SEARCH` (Phase 4)
  - Vertex AI Vector Search (Phase 5+)
  - Elasticsearch / OpenSearch / 専用 DB

> Port/Adapter で切り出してあるため、phase が進んでも置換だけで済む。

---

## ベクトルはどう動くか

1. 物件タイトル + 説明 + 設備を整形
2. `multilingual-e5` でベクトル化 (384 次元)
3. `embeddings` テーブル (pgvector) に保存
4. クエリも同じモデルでベクトル化
5. cosine 距離 (`<=>`) で近傍検索
6. 上位 N 件を **意味候補** として返す

> 物件側ベクトルは `make seed` で事前投入、クエリは毎回オンデマンド計算。

---

## rerank の役割と特徴量

`LightGBM LambdaRank` が見る 10 特徴量:

- 検索系: `me5_score` / `lexical_rank` / `semantic_rank`
- 物件属性: `rent` / `walk_min` / `age_years` / `area_m2`
- 行動系: `ctr` / `fav_rate` / `inquiry_rate`

→ 単一スコアではなく **総合判定** で並び替える。  
ME5 スコアは順位そのものではなく、特徴量の 1 つ。

---

## Redis の位置づけ

- 同一条件の検索結果を短時間キャッシュする
- 毎回すべてを再計算しない
- ただし検索品質の本体ではなく、応答性の補助

---

## 処理の流れ

```text
/search
  ↓
条件付き lexical 候補取得
  ↓
query embedding 作成
  ↓
semantic score 計算
  ↓
特徴量作成
  ↓
LambdaRank rerank
```

---

## 検索 MLOps の難所

- 正解データの作成が難しい
- 「良い検索結果」を数値化しにくい
- 行動ログには **表示位置バイアス** が乗る
- オフライン指標とオンライン成果が一致しない
- ユーザーごとに重視軸が違う (価格 / 駅距 / 築年 / 写真...)

> モデルだけでなく、**評価とログ設計** が改善の主戦場。

---

## なぜ精度評価が難しいか

- Phase 1 (住宅価格): 予測 3,000 万 vs 実際 3,100 万 → 誤差 100 万、明快
- Phase 3 (検索): 「札幌 1LDK 駅近」の正解は一意に決まらない
- そこで **複数指標** で見る:
  - Recall@K / Precision@K / NDCG@K / MRR
  - CTR / CVR / 問い合わせ率 / お気に入り率
- どの指標も万能ではない (クリック ≠ 良い結果)

---

## なぜ正解データ作成が難しいか

- Phase 1 の教師: 成約価格・査定価格 (数値、明確)
- Phase 3 の教師: クリック / お気に入り / 問い合わせ / 内見 / 成約
- 行動ログは「真の良さ」を表しているとは限らない
- 必要な工夫:
  - 表示位置バイアス補正
  - クエリごとの評価データ作成
  - 一部に **人手評価 / LLM-as-a-Judge**
  - オフライン / オンラインを分けて測る

## この Phase で押さえること

1. 検索は段階分担 (lexical / semantic / rerank) で見る
2. ベクトル DB は意味検索の本体、Phase ごとに置換可
3. `LightGBM` は単一スコアでなく **総合判定** の道具
4. 検索 MLOps の難所は **評価とログ設計** に集中する
5. **正解データの作り方** が品質改善の出発点
