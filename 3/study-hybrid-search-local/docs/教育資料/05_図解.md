Phase 3 の教育資料で使う図解原稿。  
ハイブリッド検索の 3 段構成が伝わるものだけを残す。

---

flowchart LR

## 図 5: 回帰 vs ランキング (Phase 1 と Phase 3 の違い)

```mermaid
flowchart LR
    subgraph Phase1["Phase 1 — 住宅価格予測 (回帰)"]
      P1in[特徴量<br/>緯度・部屋数・築年] --> P1m[XGBoost / LightGBM]
      P1m --> P1out[価格 (数値)]
      P1out --> P1eval[RMSE / MAE]
    end
    subgraph Phase3["Phase 3 — 検索 (ランキング)"]
      P3in[クエリ + 候補集合] --> P3m[LightGBM LambdaRank]
      P3m --> P3out[順位付き Top-K]
      P3out --> P3eval[NDCG / MAP / Recall@K]
    end
```

> 同じ LightGBM でも、目的関数 (二乗誤差 vs LambdaRank) と評価指標が別物。

## 図 6: ベクトル検索のデータフロー

```mermaid
flowchart LR
    Doc[物件タイトル + 説明 + 設備] --> E5a[multilingual-e5]
    E5a --> Vec[(pgvector embeddings<br/>384 dim)]
    Q[ユーザクエリ] --> E5b[multilingual-e5]
    E5b --> Sim["cosine 距離 (`<=>`)"]
    Vec --> Sim
    Sim --> Top[意味的に近い候補]
```

> 物件側ベクトルは `make seed` で事前投入、クエリ側は毎回オンデマンド。

---

## 図 7: 評価データの難しさ

```mermaid
flowchart TB
    Log[行動ログ<br/>click / favorite / inquiry]
    Bias[表示位置バイアス<br/>写真の見栄え<br/>価格の安さ]
    Bias -.->|混入| Log
    Log --> Eval{これは本当に<br/>「良い結果」?}
    Eval -->|補正策| H1[人手評価]
    Eval -->|補正策| H2[LLM-as-a-Judge]
    Eval -->|補正策| H3[A/B テスト]
    H1 --> Truth[評価データ]
    H2 --> Truth
    H3 --> Truth
```

> 行動ログだけでは「真の良さ」は測れない。複数チャネルで補正するのが実案件の作法。
